# Week 14. 내 에이전트 최종 정리와 제출 준비

> 이번 주에는 새 개념을 배우지 않는다.
> 

> 11~13주차에 만든 본인의 에이전트를 실행 가능한 상태로 정리하고, 최종 제출물과 발표 자료를 완성한다.
> 

> 기본형은 규칙 기반 에이전트이고, 중급형 이상은 Groq API, 외부 도구, LangGraph 중 일부를 선택적으로 사용한다.
> 

---

## 학습 목표

- 최종 제출 기준에 맞게 파일을 정리한다.
- 다른 사람이 README만 보고 실행할 수 있게 만든다.
- 실행 결과와 한계를 설명할 수 있게 준비한다.
- 본인 프로젝트의 구현 수준을 기본형·중급형·확장형·심화형 중 하나로 설명한다.
- 코딩에이전트를 사용해 오류 수정, 문서 정리, 발표자료 초안을 만든다.
- 15주차 발표를 위한 1분 데모 흐름을 만든다.

---

## 이번 주 핵심 원칙

1. 새 기능을 크게 추가하지 않는다.
2. 실행이 안 되는 코드를 제출하지 않는다.
3. README, 출력 예시, 도구 사용 기록을 반드시 남긴다.
4. 코딩에이전트가 만든 설명이 실제 코드와 맞는지 확인한다.
5. API 키는 절대 GitHub에 올리지 않는다.
6. 발표는 “무엇을 만들었는가, 어떻게 나누었는가, 어디까지 되는가”를 중심으로 한다.

## 14.0 구현 수준 정리

최종 제출은 아래 네 수준 중 하나로 정리한다. 높은 수준을 억지로 선택할 필요는 없다. 중요한 것은 본인이 구현한 범위를 정확히 설명하는 것이다.

| 수준 | 기준 |
| --- | --- |
| 기본형 | 규칙 기반 함수 에이전트. 외부 API 없이 `python my_agent.py` 실행 가능 |
| 중급형 | Groq API를 추출 또는 검토 중 하나에 사용. 규칙 기반 fallback 있음 |
| 확장형 | 외부 API 또는 도구 1개 이상 사용. 도구 실패 시 기본 실행 가능 |
| 심화형 | LangGraph로 상태, 분기, 반복 중 하나 이상을 명시적으로 구성 |

제출과 발표에서 반드시 다음을 말한다.

- 내가 선택한 구현 수준
- 그 수준을 선택한 이유
- API나 외부 도구가 실패해도 어디까지 실행되는지
- 아직 자동화하지 않은 부분

## 14.1 최종 제출 파일

최종 제출 GitHub 저장소에는 다음 파일이 있어야 한다.

```
my_agent.py
sample_input.txt
output.md
output_user_guide.md
review_report.md
README.md
context.md
todo.md
.github/copilot-instructions.md
tool_usage_log.md
presentation.md
```

Groq API나 외부 도구를 사용했다면 다음 파일도 추가한다.

```
requirements.txt
.env.example
```

파일별 역할은 다음과 같다.

| 파일 | 설명 |
| --- | --- |
| `my_agent.py` | 최종 실행 코드 |
| `sample_input.txt` | 본인 에이전트의 입력 예시 |
| `output.md` | 핵심 정보 추출 결과 표 |
| `output_user_guide.md` | 사용자나 상황별 최종 출력문 |
| `review_report.md` | 검토자 에이전트의 점검 결과 |
| `README.md` | 실행 방법과 프로젝트 설명 |
| `context.md` | 프로젝트 목표와 제약 |
| `todo.md` | 개발 과정과 남은 일 |
| `.github/copilot-instructions.md` | Copilot 작업 규칙 |
| `tool_usage_log.md` | 코딩에이전트 사용 기록 |
| `presentation.md` | 발표자료 초안 |
| `requirements.txt` | 선택 확장을 위해 설치한 패키지 목록 |
| `.env.example` | 필요한 환경변수 이름 예시. 실제 키는 쓰지 않음 |

## 14.2 실행 점검

먼저 실행한다.

```bash
python my_agent.py
```

실행 후 다음 파일이 생성되거나 갱신되는지 확인한다.

```
output.md
output_user_guide.md
review_report.md
```

Groq API나 외부 도구를 사용했다면 API 키가 없는 상태에서도 한 번 실행해 본다. 이때 최소한 규칙 기반 기본 결과는 생성되어야 한다.

실행 오류가 있으면 새 기능을 추가하지 말고 오류만 고친다.

```
my_agent.py를 실행했더니 아래 오류가 나왔어.
새 기능을 추가하지 말고, 실행 오류만 고쳐줘.
기존 함수 이름과 전체 흐름은 유지해줘.

(오류 메시지)
```

## 14.3 README 최종 정리

README에는 다음 항목이 있어야 한다.

```markdown
# 내 에이전트 이름

## 한 문장 설명

## 해결하려는 문제

## 실행 방법

## 입력 파일

## 출력 파일

## 에이전트 역할
| 역할 | 함수 | 설명 |
|---|---|---|

## 사용한 코딩에이전트

## 구현 수준
- 기본형 / 중급형 / 확장형 / 심화형:

## 사용한 API 또는 외부 도구
- 없음 / Groq API / 외부 API / LangGraph:

## 현재 한계
```

코딩에이전트 요청:

```
현재 파일을 기준으로 README.md를 최종 정리해줘.
실제로 구현되지 않은 기능은 쓰지 마.
실행 방법은 python my_agent.py 하나로 설명해줘.
에이전트 역할은 함수 이름과 연결해서 표로 정리해줘.
구현 수준을 기본형, 중급형, 확장형, 심화형 중 하나로 적어줘.
Groq API나 외부 도구를 사용했다면 필요한 환경변수와 fallback 동작을 설명해줘.
현재 한계도 솔직하게 써줘.
```

## 14.5 발표자료 만들기

발표자료는 길 필요가 없다. `presentation.md`에 다음 순서로 작성한다.

```markdown
# 내 에이전트 발표

## 1. 문제
내 에이전트가 해결하려는 문제를 한두 문장으로 쓴다.

## 2. 만든 것
입력 자료를 받아 어떤 결과를 만드는지 설명한다.

## 3. 멀티에이전트 구조
핵심 정보 추출자 → 분류자 → 출력 작성자 → 검토자

## 4. 구현 수준
기본형 / 중급형 / 확장형 / 심화형 중 하나를 적는다.

## 5. 실행 결과
output.md, output_user_guide.md, review_report.md

## 6. 사용한 코딩에이전트와 외부 도구
Copilot / Gemini CLI / Antigravity 사용 내용

## 7. 한계
정교한 자연어 이해는 부족하다. 입력 형식이 크게 바뀌면 오류가 날 수 있다.
```

코딩에이전트 요청:

```
README.md와 출력 파일을 바탕으로 presentation.md 초안을 만들어줘.
발표 시간은 3분이다.
문장은 짧게 쓰고, 실제 구현된 내용만 포함해줘.
내 에이전트 주제에 맞게 제목과 예시를 바꿔줘.
구현 수준과 사용한 외부 도구가 있다면 포함해줘.
```

## 14.6 1분 데모 흐름

발표 전에 다음 흐름을 1분 안에 보여줄 수 있어야 한다.

```
1. sample_input.txt를 보여준다.
2. python my_agent.py를 실행한다.
3. output.md 표를 보여준다.
4. output_user_guide.md 최종 출력문을 보여준다.
5. review_report.md 검토 결과를 보여준다.
6. Groq API나 외부 도구를 썼다면 어디에 쓰였는지 짧게 설명한다.
```

데모 중 설명할 문장:

```
이 프로젝트는 입력 자료를 받아 핵심 정보 추출, 분류, 최종 출력 작성, 검토의 네 역할로 나누어 처리합니다.
```
